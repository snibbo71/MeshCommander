# Native macOS MeshCommander — Implementation Plan

## Status (updated 2026-07-23)

**Phases 0, 1, 2, and 3 are implemented and verified end-to-end against real Intel AMT hardware.** Core AMT management (power control, hardware inventory, event log, network config), network discovery/scan, KVM remote desktop, and SOL terminal all work. **Phase 4 (IDER) is implemented; mounting a disk image over IDE-R works against real hardware, but the target server never actually boots from the mounted media** — most likely a firmware-level limitation (legacy/CSM boot support, or the board only having Intel Standard Manageability rather than full AMT) rather than an app bug; see Findings item 11. **Parked, not a priority** — the user doesn't rely on this feature day-to-day and will use physical USB media instead when needed. Phase 5 (certificates CRL/OCSP cache, embedded boot-media server, signing/notarization/DMG packaging) is not yet started.

The rest of this document is the original pre-implementation plan, left mostly intact for context, plus a **"Findings from implementation"** section covering what changed, what the plan got wrong, and gotchas worth knowing before continuing into Phase 4/5.

## Findings from implementation (read this before touching Phase 4/5)

1. **The `crypto` shim in `node-shim.js` had to be a real implementation, not an inert stub.** The plan assumed `require('crypto')` was unused since digest auth uses `hex_md5` directly, but the local computer-list persistence path (`saveComputers`/`loadComputers` in index.html, reachable as soon as one computer is added) uses real `require('crypto').randomBytes`/`createCipher`/`createDecipher` (AES-256-CTR via legacy EVP_BytesToKey/MD5 key derivation). Implemented for real, backed by forge (already vendored for Certificates) plus `window.crypto.getRandomValues` for actual CSPRNG randomness. Since this data only ever round-trips through this same shim, OpenSSL byte-for-byte compatibility didn't strictly matter, but was implemented anyway since it was no extra work.

2. **Excluding a feature that "sounds" separable can silently break the app, with no thrown error, because of unconditional (non-marker-gated) references elsewhere in the vendor code.** This happened twice:
   - Excluding `CertificateManager`/`USBSetup` (per the plan's original Phase 1 exclude list): `startup()` in the giant inline `<script>` block unconditionally does `QS('id_certManagerPanel').left = '52px'` with no marker guard around that specific line, even though the element itself is marker-gated. `QS()` catches `Q(x)` returning null internally, but the outer `.left = ...` assignment on `QS()`'s `undefined` return throws, uncaught, and `startup()` aborts before ever calling `go(101)`. Symptom: the app hangs forever on the static "Loading..." placeholder baked into the HTML, with **no console error visible** unless Safari's Web Inspector was already attached before the crash (it does not replay historical console errors — this cost significant back-and-forth to diagnose).
   - Excluding `Inflate` while including `Desktop` (Phase 3): `amt-desktop-0.0.2.js` unconditionally does `obj.inflate = ZLIB.inflateInit(-15)` at KVM object construction time (not lazily, not gated on whether the negotiated encoding actually uses zlib), throwing `ReferenceError: Can't find variable: ZLIB` the moment `Desktop` is enabled without `Inflate`.

   **Fix applied both times:** include the "optional" feature anyway (`CertificateManager`, `USBSetup`, and `Inflate` are all now in `Scripts/features-phase3.json`). **Lesson for Phase 4/5:** before excluding any feature the plan doesn't strictly need, `grep` the actual vendor `.js` file(s) it gates for capitalized global identifiers and unconditional (non-`###BEGIN###`-wrapped) references, rather than trusting the feature name's apparent scope. Don't assume the exclude list in this plan is safe as originally written.

3. **`node-shim.js`'s `Buffer` had to become a real `Uint8Array` subclass, not a string-wrapper object.** Phase 1 only ever needed `new Buffer(str, 'binary')` immediately before a `socket.write()`, so a simple `{ __mcBinary: str }` wrapper with a `.toString()` sufficed. Phase 2/3 broke that: `amt-scanner-0.1.0.js` builds RMCP packets with direct indexed byte writes (`packet[9] = tag`) and reads (`data[12]`), and `amt-redir-node-0.1.0.js` calls `new Buffer(uint8ArrayOrPlainArray)` with no encoding argument at all. Fixed by making `Buffer extends Uint8Array` (mirroring how modern real Node's `Buffer` is implemented), which gives indexed access, `instanceof Buffer`, and array-like construction all at once.

4. **UDP discovery (Phase 2) needed a different Swift transport than TCP/TLS, not just an extension of `NetworkBridge`.** `NWConnection` is connection-oriented (bound to one remote host:port); `amt-scanner-0.1.0.js`'s actual usage — bind one local ephemeral port, `sendto()` many different destination IPs in a range, `recvfrom()` replies from whichever IP answers — doesn't fit that model well. Implemented as a separate `DatagramBridge.swift` using raw BSD sockets (`socket`/`bind`/`sendto`/`recvfrom` via Darwin, wrapped in a `DispatchSourceRead`), registered as a second WKScriptMessageHandler `"mcDgram"`, alongside a `getnameinfo`-based DNS reverse lookup for `dns.reverse()`. This mirrors Node's own dgram implementation more directly than fighting Network.framework's abstractions would have.

5. **`NWConnection` has no built-in connect timeout, and a wrong/unreachable IP hangs forever with zero feedback**, not because of a slow OS timeout, but because Network.framework parks an unreachable connection in `.waiting` state indefinitely rather than transitioning to `.failed` — and the original code's `default: break` in the state-update switch silently ignored `.waiting`. Fixed with an explicit 10-second connect-phase `DispatchSourceTimer` in `NetworkBridge.swift` (separate from the JS-driven post-connect idle timer), which cancels the connection and emits `error`+`close` if `.ready` isn't reached in time.

6. **Debugging aids added, not in the original plan, worth keeping:**
   - `webView.isInspectable = true` (macOS 13.3+, debug builds) in `WebViewController.swift`, so Safari's Web Inspector can attach to the `file://`-loaded WKWebView.
   - A `window.onerror` hook in `node-shim.js` forwards uncaught JS exceptions to Swift's stdout via the existing `mcNet` bridge (op `jserror`), so running the built binary directly from Terminal (not via `open`, which detaches stdout) surfaces crashes immediately without needing to reattach Web Inspector every time.

7. **Tooling gotcha:** xcodegen's `info.path`/`entitlements.path` fully regenerate the target plist from `info.properties` on every `xcodegen generate` run — hand-edited keys not listed in `properties` get silently wiped. Declare all custom Info.plist keys via `properties` in `project.yml`.

8. **Environment gotcha (not project-specific):** a screen-recording/accessibility-restricted CLI sandbox can build and run the app but can't screenshot it or drive its UI — that verification loop needs a human with real desktop access. Don't burn many tool-call round-trips on blind terminal-only workarounds when a bug needs visual/interactive confirmation; ask the user to check (e.g. Web Inspector) sooner rather than later.

9. **Phase 4 (IDER) turned out to need zero new native bridge code, contradicting the original Phase 4-5 sketch.** The sketch assumed `amt-ider-ws-0.0.1.js`'s `File`/`FileReader` calls (for reading the local `.img`/`.iso` the user picks to mount) would need swapping for a native `NSOpenPanel`+`FileHandle` bridge. They don't: `iderStart()`/`iderStart2()` in `index.html` use plain `<input type=file>` + `Q(...).files[0]` + the vendor file's own `new FileReader()`/`.slice()` — all standard DOM APIs that WKWebView already supports natively even under a `file://`-loaded page (confirmed working already via the `CertificateManager` cert-import flow from Phase 1, which uses the same pattern), with no `require()` call anywhere in the mount path. Grepped `amt-ider-ws-0.0.1.js` and every `ider`-related line in `index.html` for the same class of unconditional-reference bug as Findings item 2 (the only prior occurrences of `require(...)` in that file are inside the `IDERDebug` marker block, gated and excluded); found none. Added `Scripts/features-phase4.json` (phase3 + `IDER`, `IDERStats`; deliberately still excluding `IDER-IMRSDK` — Windows-only IMRSDK.dll, no macOS equivalent, matches the original plan — and `Mode-MeshCentral2`/`IDERDebug`). Build succeeds, and running the built binary directly from Terminal shows no `jserror` and the process stays alive (no repeat of the silent-hang class of bug). **Not yet tested against real hardware** — actually mounting an `.img`/`.iso` on the user's AMT device is the remaining verification step, plus the `IDER-IMRSDK` exclusion assumption should still be sanity-checked if a Windows build is ever attempted.
10a. **`<input type=file>` silently does nothing in a macOS WKWebView unless a `WKUIDelegate` implementing `webView(_:runOpenPanelWith:initiatedByFrame:completionHandler:)` is set.** This is *not* automatic the way it is in Safari — no `uiDelegate` was ever set on the app's `WKWebView` (`WebViewController.swift` only configured message handlers, not `uiDelegate`), so clicking any file-picker button (IDER's floppy/CDROM inputs, `CertificateManager`'s cert import, the computer-list import/export) did nothing, with zero console output — no error to catch, just an inert click. **This invalidates the earlier claim in this doc that the `CertificateManager` cert-import flow already proved file inputs work** — that was an unverified assumption, not a tested fact; flagging so future-me doesn't repeat "X already works elsewhere" without checking. Fixed by adding a `WebViewUIDelegate: NSObject, WKUIDelegate` in `WebViewController.swift` that opens an `NSOpenPanel` and forwards the chosen URLs to WebKit's completion handler, wired via `webView.uiDelegate = delegate`. Confirmed via grep that native `alert()`/`confirm()`/`prompt()` (which also silently no-op without a `uiDelegate`) are not otherwise depended on — the one `alert(...)` call in `index.html` is behind a debug-only `urlvars['webcn']` condition.
11. **Real-hardware result: IDER mount succeeds (media readable, byte counters move), but the server doesn't boot from it — parked, not further debugged per user request.** Likely causes, not yet confirmed: IDE-R redirects via legacy INT13 emulation, which many UEFI-only server boards don't support without CSM/Legacy boot mode enabled; alternatively the board may only have Intel Standard Manageability (ISM) rather than full AMT, which doesn't support IDE-R/KVM at all (only power control + SOL). Diagnostic steps identified but not run: check BIOS for CSM/Legacy toggle, check whether AMT_RedirectionService reports IDE-R as an enabled capability (vs. just SOL/power), try entering the one-time boot menu (BIOS Setup checkbox + IDER mounted) to see if a redirected-CD entry even appears. **User doesn't rely on this feature and will use physical USB media instead** — resume only if it becomes relevant again.
10. **Mounting media via IDER isn't enough to make the target machine boot from it — `PowerControl-Advanced` is also required.** Starting an IDER session only makes the image available over the redirection channel; actually booting from it needs a one-time BIOS boot-order override (`AMT_BootSettingData` with `UseIDER=true`/`IDERBootDevice`), which in this codebase is exclusively exposed through the "Set boot options" advanced power dialog (`dialog24`/`showAdvPowerDlg()`, `action==999`) — the plain `PowerControl` quick actions (Power up/Reset/Power cycle/Power down) don't touch boot source at all. This dialog was on the original plan's "still excluded" list (deferred as a Phase-1-unnecessary nice-to-have), but it's a hard requirement for exercising IDER end-to-end, not optional for Phase 4. Added to `features-phase4.json`; rebuilt and re-verified clean launch (no `jserror`).

## Context

MeshCommander (this repo, forked to `snibbo71/MeshCommander` from `Ylianst/MeshCommander`) is Intel's Active Management Technology (AMT) console. The user wants a genuinely **native** Mac app — not an Electron wrapper — distributed as a signed, notarized DMG via their existing Apple Developer account, with full feature parity including IDE-Redirection (mounting virtual boot media on remote AMT hardware).

The app talks to AMT devices over raw TCP/TLS sockets (ports 16992/16993) and UDP (RMCP discovery ping, port 623). That requires Node's `net`/`tls`/`dgram`/`dns` modules, which a plain `WKWebView`'s JS context doesn't have — there's no `require()`. The repo's only existing "desktop" build target is NW.js (Chromium+Node merged runtime; confirmed via `package.json`'s NW.js manifest fields and `output/index.htm`'s unconditional `require('nw.gui')` calls) — there is no native shell to mirror, and no Electron scaffolding exists either.

The good news from research: the vast majority of the app (WSMAN protocol logic, KVM rendering, terminal emulation, certificate handling, the IDER wire protocol) is portable, transport-agnostic JS with **no** Node dependency. Only a narrow socket-level seam needs a native bridge. This plan originally covered **Phase 0 + Phase 1**: a working native app shell with core AMT management working end-to-end against real hardware. That milestone, plus Phases 2 and 3, are now done (see Status above). Phases 4-5 are sketched at the end so the design doesn't paint us into a corner, but are not yet implemented.

## Architecture decisions

- **AppKit, not SwiftUI.** The entire UI lives inside a `WKWebView`; AppKit gives precise `NSWindow` sizing control (matching `package.json`'s `window: {width:970, min_width:970, height:760, min_height:640}`) and a natural imperative style for the message-handler bridge.
- **Load via `file://` + `loadFileURL`, not a custom `WKURLSchemeHandler`.** The JS has no module system — plain `<script src="...">` tags with global-scope load order — so `file://` resolves relative paths exactly like a static site, and `localStorage` persists reliably at a fixed bundle path.
- **Our own build-time HTML preprocessor**, replacing the proprietary Windows-only "WebSite Compiler". `index.html` is a template full of `<!-- ###BEGIN###{FeatureName} --> ... <!-- ###END###{FeatureName} -->` marker blocks (also as `// ###BEGIN###{...}` inside script blocks, with `!Name` negation and nesting). We write a small Node script to strip/keep named blocks per a feature-list JSON, mirroring what the `.wcc` config tool does.
- **Binary data across the JS↔Swift bridge uses base64**, via JS's native `btoa`/`atob` (the codebase already treats socket data as one-JS-char-per-byte "binary strings" via `setEncoding('binary')`, and already round-trips certificate/file bytes through `atob`/`btoa` elsewhere) and Swift's `Data(base64Encoded:)`/`.base64EncodedString()`. **No changes needed to `amt-wsman-node-0.2.0.js` itself.**
- **Non-sandboxed, Developer ID signed** (DMG distribution, not App Store) — no special entitlements needed for outbound `Network.framework` connections. (Not yet actually signed with a real Developer ID — local builds use ad-hoc `CODE_SIGN_IDENTITY: "-"`. Real signing/notarization is Phase 5.)
- **TLS handling**: `NWProtocolTLS.Options` with explicit min/max TLS version (replacing the legacy `SSL_OP_*`/`secureProtocol` flags used for old AMT firmware) and a permissive `sec_protocol_options_set_verify_block` (accept at transport layer) — because the JS layer already does its own certificate **fingerprint pinning** (`xtlsFingerprint`/`xtlsCheck` in `amt-wsman-node-0.2.0.js`) against self-signed AMT certs, which we preserve as-is rather than duplicating/fighting it with strict native trust validation.

## Two load-bearing findings from research (both verified directly)

1. **`hex_md5`/`rstr_md5` (required for HTTP Digest auth — called unconditionally at `amt-wsman-node-0.2.0.js:134`) do not exist in the base `amt-0.2.0.js`.** They only exist inside the localized variant files, gated behind the `Certificates` marker. Verified directly: `amt-0.2.0_fr.js:867` (forge-based, used when `Certificates` is enabled — which it is for us) and a TinyMD5 fallback at line 880 (used when `Certificates` is disabled). **Without vendoring this in, the first 401 challenge from any AMT device throws `ReferenceError` and every connection silently fails.** Fix: a 1-line `md5-shim.js` containing the forge-based version from `amt-0.2.0_fr.js:867`, loaded after `forge.bundle.js`. (Implemented and verified — see Findings item 1 above for the closely-related `crypto` shim finding.)
2. **Enabling `Mode-NodeWebkit` (required to get the raw-socket transport) also activates ~40 other scattered `require('nw.gui')`/`fs`/`os`/`child_process` call sites** throughout `index.html` (argv parsing, window title/menu management, encrypted-list saving, IDER OS checks, etc.) — because marker state is global per name, not scoped to one script block. All of these are either Windows-only-reachable or non-critical for Phase 1, so `node-shim.js`'s `require()` needs a wider (but shallow, mostly-stub) surface than just `net`/`tls`. (Implemented — see the actual `node-shim.js` module table for the final surface, which grew further in Phase 2/3 for `dgram`/`dns`/real `Buffer`.)

## Build-time HTML preprocessor

- **Tool**: `Scripts/build-html.js` (Node.js, build-time only, run as an Xcode "Run Script" build phase, or manually via `node Scripts/build-html.js --features Scripts/features-phaseN.json`). Never edits vendor files in place — reads `index.html` from repo root, writes `MeshCommanderMac/Resources/index-mac.html` (generated, gitignored).
- **Algorithm**: single-pass regex scan matching both comment styles for BEGIN/END markers, maintaining a stack of `{name, keep}` frames where a child frame's effective-keep is computed as `ownKeep AND parent's effectiveKeep at push time` (captured immutably) — this correctly handles even the one instance of non-well-nested crossing markers found in the wild (`PowerControl-Advanced`/`PowerControl-OneClick`) without needing strict LIFO BEGIN/END matching. A block is kept iff its own flag matches enabled-list membership (accounting for `!name` negation) AND every enclosing block is kept. Always strips `**`-prefixed blocks (Closure Compiler externs). Replaces the `webcompilerfeatures` placeholder token. Inserts `<script src="node-shim.js">` before `common-0.0.1.js`'s tag, and `<script src="md5-shim.js">` after the `Certificates` block's forge/certificates script tags. Asserts the marker stack is empty at EOF; fails loudly if not. Also auto-copies every local (`src=`/`href=`) asset the generated HTML references, plus wholesale-copies `images-commander/`, `images/`, and favicons (since some image paths are built via runtime string concatenation in JS, not static attributes).
- **`Scripts/features-phase1.json` / `features-phase2.json` / `features-phase3.json`** — one file per milestone, each a superset of the previous (phase3 ⊃ phase2 ⊃ phase1), derived from `websitecompiler/NodeWebkit-Commander.wcc`'s real `FeatureList` (recovered via `strings`) and adjusted per the hard-dependency lessons above:
  - **Phase 1** (`features-phase1.json`): `Look-Commander, ComputerSelector, ComputerSelector-Local, ComputerSelectorToolbar, ContextMenus, Mode-NodeWebkit, Certificates, HardwareInfo, EventLog, AuditLog, NetworkSettings, RemoteAccess, SystemDefense, PowerControl, Storage, Wireless, WsmanBrowser, CertificateManager, USBSetup` (the last two added after the "Loading..." hang was diagnosed — see Findings item 2).
  - **Phase 2** (`features-phase2.json`): phase 1 plus `ComputerSelectorScanner`.
  - **Phase 3** (`features-phase3.json`): phase 2 plus `Terminal, Terminal-Enumation-All, Terminal-FxEnumation-All, TerminalSize, Inflate, Desktop, DesktopFocus, DesktopType, DesktopRotation, Desktop-Settings, Desktop-Multi` (`Inflate` added after the KVM `ZLIB` crash — see Findings item 2; the `Desktop*` sub-features are all small additive UI bits bundled together in the real product's tested "FullSite" profile, included defensively even though most are individually marker-guarded, to minimize risk of the same class of bug).
  - **Phase 4** (`features-phase4.json`): phase 3 plus `IDER, IDERStats, PowerControl-Advanced` (`PowerControl-Advanced` added because it's the only UI path to the one-time boot-to-IDER override needed to actually boot from mounted media — see Findings item 10; `IDER-IMRSDK`/`Mode-MeshCentral2`/`IDERDebug` still excluded, see Findings item 9).
  - Still excluded (deferred to later phases or dropped, per the original plan — **re-verify with a grep before trusting this list for Phase 5**): `IDER-IMRSDK, MeshServerConnect, Mode-MeshCentral2, Mode-LMS, Mode-WebSite, Mode-Firmware, PowerControl-OneClick, DesktopInband, DesktopInbandFiles, Scripting*, SessionRecording, TerminalReplay, FileSaver, VersionWarning` (the last one specifically to avoid an unplanned external network fetch).

## `node-shim.js` (loaded first, before `common-0.0.1.js`)

Provides a fake `require()` covering: `net` (a `Socket` constructor), `tls` (`.connect()`), `dgram` (a `Socket`-like object bridged to `DatagramBridge.swift`/"mcDgram" — Phase 2), `dns` (`.reverse()`, also via "mcDgram"), `crypto` (a **real** implementation — `randomBytes`/`createCipher`/`createDecipher`, forge-backed, see Findings item 1), `constants`/`os`/`path`/`fs`/`util` (mostly stubs, some now with light real behavior), plus a `require('nw.gui')` stub (`App.argv`, `Window.open/get`, `Shell.openExternal`, inert `Menu`/`MenuItem`) and a bare `process` object.

**`Buffer`** is a real `Uint8Array` subclass (not a string wrapper — see Findings item 3), supporting `new Buffer(str, encoding)`, `new Buffer(size)`, and `new Buffer(uint8ArrayOrArray)`, plus `.toString(encoding)` for `'hex'`/`'base64'`/binary passthrough.

Core design for `net`/`tls`: each JS "socket" gets a sequential id, stored in `window.__mcNetSockets`. Outbound calls (`connect`/`write`/`setTimeout`/`destroy`/`end`) go via `window.webkit.messageHandlers.mcNet.postMessage({op, id, ...})`. Inbound events arrive via a single global `window.__mcNetCallback(id, event, payload)` that Swift invokes through `webView.evaluateJavaScript(...)`, dispatching to the per-socket `data`/`close`/`timeout`/`error`/`connect` handler arrays. `write()` does `btoa(binaryString)` before posting; the callback does `atob(payload.dataB64)` before handing data to the existing `xxOnSocketData` handlers — so `amt-wsman-node-0.2.0.js` and `amt-redir-node-0.1.0.js` require zero modification. `setNoDelay()` is a deliberate no-op on the JS side (Swift always enables TCP_NODELAY unconditionally).

**`dgram`/`dns` (Phase 2)** follow the identical id-keyed/callback-dispatch shape, but over a second message handler `"mcDgram"` and global callback `window.__mcDgramCallback(id, event, payload)` (plus a request-id-keyed `window.__mcDnsCallback(reqId, payload)` for the one-shot `dns.reverse()` calls). See `DatagramBridge.swift` below for why this is a separate bridge from `net`/`tls`.

An uncaught-exception `window.onerror` hook forwards to Swift's stdout via `mcNet` (op `jserror`) for fast terminal-only debugging (see Findings item 6).

## Swift-side `NetworkBridge`

One `NSObject, WKScriptMessageHandler` class owning an `[Int: NWConnection]` dictionary plus a per-connection idle-timer and connect-phase timer, on a private serial queue.

- **`connect`**: builds `NWParameters` — `NWProtocolTCP.Options` with `noDelay = true`; for `kind:"tls"`, an `NWProtocolTLS.Options` with `sec_protocol_options_set_min/max_tls_protocol_version` (legacy AMT default ~TLS 1.0–1.2) and a permissive `sec_protocol_options_set_verify_block` (JS does fingerprint pinning separately). `stateUpdateHandler` fires `"connect"` (with peer certificate fingerprint/raw bytes extracted via `sec_protocol_metadata_access_peer_certificate_chain`/`SecCertificateCopyData`, SHA-1 colon-hex to match Node's default fingerprint format) on `.ready`, `"error"`+`"close"` on `.failed`, `"close"` on `.cancelled`. Starts a recursive `conn.receive(...)` loop feeding `"data"` events.
- **Connect-phase timeout (added after implementation, not in the original plan — see Findings item 5)**: a 10-second `DispatchSourceTimer` armed alongside `nwConnection.start()`; if `.ready` isn't reached in time (including the `.waiting` state that `NWConnection` silently sits in forever for an unreachable host, with no `default: break` fallback), cancels the connection and emits `error`+`close` so the JS layer's own retry/error-surfacing logic can take over instead of hanging with zero feedback.
- **`write`**: decodes base64, `conn.send(...)`.
- **`setTimeout`**: `NWConnection` has no built-in idle timeout — implemented directly via a `DispatchSourceTimer` per connection, reset on every write/receive, firing a `"timeout"` event on expiry (matching Node's `timeout` event semantics, which doesn't itself close the socket — the JS layer already handles that via its own `xxOnSocketClosed` wiring).
- **`destroy`/`end`**: `conn.cancel()`.
- Cleanup: window-close / app-terminate cancels all live connections (`cancelAll()`).
- **`CertificateFingerprint.swift`**: small helper extracting the DER leaf cert and computing the colon-hex SHA-1 fingerprint string.

## Swift-side `DatagramBridge` (Phase 2, not in the original plan's Phase 1 scope)

A second `NSObject, WKScriptMessageHandler`, registered as `"mcDgram"`, using **raw BSD sockets** (`socket`/`bind`/`sendto`/`recvfrom` via Darwin) rather than `Network.framework`, because `NWConnection`'s connection-oriented model doesn't fit `amt-scanner-0.1.0.js`'s actual bind-once/sendto-many-different-peers/recvfrom-from-any-of-them usage pattern (see Findings item 4).

- **`bind`**: opens a `SOCK_DGRAM`/`IPPROTO_UDP` socket, binds to the given local port (0 = ephemeral), sets up a `DispatchSourceRead` on the fd that calls `recvfrom()` and emits `"message"` events with `{dataB64, address, port}`.
- **`send`**: `sendto()` to an arbitrary destination address:port, no prior "connection" needed.
- **`close`**: cancels the read source (which closes the fd in its cancel handler).
- **`dnsReverse`** (a one-shot request, not a persistent socket): `getaddrinfo`/`getnameinfo` on a background queue, replying via a request-id-keyed JS callback rather than the id-keyed socket registry.
- Cleanup: `cancelAll()`, called from the same window-close/app-terminate path as `NetworkBridge`.

## Verification

**Hardware-free (run first):**
